Architecture · System Design

Customer Support Router Agent

Live Demo — AI Problem Deconstruction & Rapid Prototyping

A working AI agent that classifies customer support tickets, retrieves relevant policies from a vector store, decides whether to resolve autonomously or escalate to a human — and logs every decision to an audit trail. This guide deconstructs the agent into its wire-level components and shows how an AI PM thinks about building production-grade autonomous systems.

🧠 What Does This Agent Look Like?

The Mental Model

Imagine a human support agent sitting at a desk. They have ears & eyes (read the message, detect mood), a policy binder (flip to the right page), a brain with judgment (can I handle this or do I need a manager?), and hands & a phone (resolve or escalate). Now replace the human with an AI agent. The architecture is identical.

👂 Perception perception.py

LLM-powered intent classifier. Extracts intent (refund, password_reset, billing, unknown), sentiment (neutral → angry), urgency (low/med/high), and entities (order_id, amount, email) using Pydantic structured output.

📚 Memory memory.py

ChromaDB vector store loaded at startup with 4 knowledge base articles. At runtime, semantic search retrieves only the top-2 most relevant policy documents — saving tokens and improving accuracy.

🧠 Reasoning reasoning.py

Decision engine that compares intent against retrieved policies. Outputs confidence score (0.0–1.0). Critical: post-LLM hardcoded guardrail forces escalation if confidence < 0.70, even if the LLM says 'resolve'.

⚡ Action action.py

Executes the decision: mock Stripe refund or SendGrid password reset for resolves, mock Zendesk ticket creation for escalations. Every single decision is logged to audit_trail.jsonl (episodic memory).

🎚️ The Autonomy Spectrum

This agent doesn't have a binary ON/OFF switch. It operates on a graduated autonomy dial — the single most important concept for an AI PM. High-stakes actions require human oversight; low-risk routine tasks are handled autonomously.

🟢 ZONE GREEN — Fully Autonomous
  • Password resets (clear match, low risk)
  • FAQ answers (exact knowledge base match)
  • Small refunds ≤ $50 (within policy threshold)
🟡 ZONE YELLOW — Supervised / Approval Required
  • Medium refunds $50–$200 (agent proposes, human approves)
  • Account changes (agent summarizes, human confirms)
🔴 ZONE RED — Mandatory Human Escalation
  • Refunds > $200 (too high-risk for automation)
  • Angry sentiment + legal threats
  • Unknown intents (no policy match)
  • Account deletion requests
  • Agent confidence < 0.70 threshold
Key Insight: The agent's guardrail is not in the LLM prompt alone. There is a hardcoded post-LLM confidence override in reasoning.py (lines 77-80): even if the LLM says 'resolve,' if the confidence is below 0.70, the code forces escalation. This is the difference between a toy demo and a production agent.

💡 Key Technical & Functional Concepts

01
Structured Output via Pydantic

The LLM never returns raw text that we regex-parse. Every response is forced into a strict Pydantic schema. This means: no ambiguous outputs, engineering never debates 'what did the model mean?', and every response is unit-testable.

class MessageIntent(BaseModel):
    intent: str       # "refund", "password_reset", "billing_question", "unknown"
    urgency: str      # "low", "medium", "high"
    sentiment: str    # "positive", "neutral", "negative", "angry"
    entities: ExtractedEntities  # { order_id, amount, email }
02
Semantic Memory via Vector Store

The agent doesn't stuff all 4 policy documents into the prompt every time (that wastes tokens). Instead, at startup all markdown files are embedded into ChromaDB. At runtime, only the top-2 most relevant documents are retrieved via semantic search. For an enterprise with 500+ merchant policies, this pattern is mandatory.

# Startup: embed all knowledge base docs
self.collection.add(documents=documents, metadatas=metadatas, ids=ids)

# Runtime: retrieve only relevant policies
results = self.collection.query(query_texts=[query], n_results=2)
03
Post-LLM Hardcoded Guardrail

The LLM generates a confidence score, but LLMs can be overconfident. So there's a hardcoded programmatic override after the LLM responds. Never rely on the LLM alone for safety-critical decisions. Deterministic code wraps probabilistic model. The threshold (0.70) is a PM-defined business constant, not an engineering detail.

# Post-LLM hardcoded safeguard: enforce confidence threshold programmatically
if decision.action_type == "resolve" and decision.confidence < CONFIG["CONFIDENCE_THRESHOLD"]:
    print("⚠️ OVERRIDE: LLM suggested resolve, but confidence too low. Forcing escalation.")
    decision.action_type = "escalate"
04
Episodic Memory / Audit Trail

Every single decision — resolve or escalate — gets written to a JSONL audit log. For financial and enterprise products, you need a full audit trail of why the AI made each decision. These logs become your eval dataset: replay 100 past decisions and ask 'Would prompt v2 have been better than v1?'

{
  "timestamp": "2026-08-25T23:30:00",
  "message": "I demand a refund of $150!",
  "parsed_intent": { "intent": "refund", "urgency": "high", "sentiment": "angry" },
  "decision": { "action_type": "escalate", "confidence": 0.65, "rationale": "..." }
}
05
Temperature Tuning by Task Type

Different tasks need different temperature settings. Classification/routing tasks use temperature=0.1 for maximum determinism. Reasoning/rationale generation uses temperature=0.2 for slightly more natural explanations. Never use high temperature for structured extraction.

# perception.py — Classification: near-zero temperature
"temperature": 0.1  # Deterministic intent classification

# reasoning.py — Reasoning: slightly higher for natural rationale
"temperature": 0.2  # Logical but readable explanations

💻 Code Walkthrough

PERCEPTION src/perception.py 
response = self.client.models.generate_content(
    model=CONFIG["MODEL_NAME"],
    contents=prompt,
    config={
        "response_mime_type": "application/json",
        "response_schema": MessageIntent,
        "temperature": 0.1,
    },
)
return MessageIntent.model_validate_json(response.text)
Calls Gemini with response_mime_type='application/json' and response_schema=MessageIntent. The model is forced to return valid JSON matching the Pydantic schema. model_validate_json() parses and validates — if the model returns garbage, it throws an error instead of silently corrupting downstream.

REASONING src/reasoning.py 
decision = AgentDecision.model_validate_json(response.text)

# Post-LLM hardcoded safeguard
if decision.action_type == "resolve" and decision.confidence < CONFIG["CONFIDENCE_THRESHOLD"]:
    print("⚠️ OVERRIDE: Forcing escalation.")
    decision.action_type = "escalate"
    decision.rationale = f"Agent override: Confidence ({decision.confidence}) below threshold."

return decision
The LLM outputs its best judgment. But the code has final say. If confidence is below the PM-defined threshold (0.70), the decision is programmatically overridden to 'escalate' — regardless of what the LLM said. This is Defense in Depth.
ACTION src/action.py 
def execute(self, original_message, intent, decision):
    if decision.action_type == "resolve":
        self._handle_resolve(intent, decision)   # Mock Stripe/SendGrid
    else:
        self._handle_escalate(original_message, intent, decision)  # Mock Zendesk
    self._log_audit(original_message, intent, decision)  # ALWAYS log
Regardless of resolve or escalate, every decision is logged to audit_trail.jsonl. This creates episodic memory — vital for compliance, debugging, and building evaluation datasets for prompt improvement.

🚨 Failure Modes & Debugging

When an agent misbehaves, debug from the outside in. Check Perception first → then Memory → then Reasoning → then Action. The model is almost never the problem.

Failure Mode Component Description Fix
Misclassified Intent Perception Agent classifies 'delete my account' as 'billing_question' Improve system prompt examples or add few-shot classification examples
Wrong Policy Retrieved Memory Returns billing FAQ when customer asked about refund Improve document chunking, add metadata filters, increase n_results
Overconfident Autonomy Reasoning LLM says confidence 0.95 on an ambiguous case Post-LLM guardrail: hardcoded threshold override (0.70). Never trust LLM confidence alone.
Silent Audit Gap Action Executes refund but forgets to log it Audit logging is in the execute() method, not in resolve/escalate — it always runs.
Stale Context Memory Agent uses outdated policy from cached retrieval Recreate ChromaDB collection on startup (as implemented) or add TTL/versioning.
Rule of Thumb: 90% of production agent failures are NOT model intelligence failures — they are plumbing failures in Perception, Action, or Memory. Always check the wiring before blaming the model.
